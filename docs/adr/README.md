## Review contract

Existing 0001/0002 keep their recorded Accepted status and implemented technical contracts. Neither their authors' status labels nor merged PRs establish named human acceptance. All 15 new records are **Proposed**, including retrospective descriptions of current code. Documentation merge is not approval for a new retention policy, financial method, data entitlement, model promotion or fee flow.

A reviewer records name, date, acceptance/requested changes/deferral and rationale in #198 or the linked PR. On acceptance, update the ADR status and link that explicit disposition. Supersede a decision with a new record rather than silently rewriting its historical rationale. Separate implementation completion from decision acceptance and from hosted rollout.

## Choices needing product or specialist input

- **Retention (#196 / 0016):** purpose, retained fields/access/duration, erasure exceptions, backup/Auth/forecast handling and deletion wording. No duration or legal conclusion is inferred.
- **Financial accounting (#182 / 0005):** cost basis, cash/FX/settlement/opening balances, supported instruments and return methodology. No tax treatment is selected.
- **Session outcomes (#157 / 0006):** calendar authority, actual origins, unknown/missing sessions and legacy-row migration. Preserve existing model targets unless separately retrained/reviewed.
- **Data rights (#184 / 0009):** actual provider/plan/use evidence and measured freshness policy. MIT does not license provider or user data.
- **Audit origins (#200 / 0013):** retire client claims or distinguish them from server-observed operations; unknown historical origins stay unknown.
- **Future paid hosting (0012):** scope, user value, costs, support/permissions and explicit future authorization. An undefined 90% score cannot trigger fees.

These reviews can proceed now; dependent implementation remains gated. #202 is a verified write-integrity fix to prioritize, not a product choice to leave unresolved.
